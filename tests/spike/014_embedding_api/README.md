# Spike 014: can the embedding API be a layer, or does it need engine surgery?

**Issue:** #682 · **Feeds:** PR #678 (spec 013 Embedding API, `Status: Proposed`)

## Hypothesis

> A `Send + Sync` connection handle over a worker-thread-owned `Rc` engine
> graph can serve incremental per-row results **and** a rows-affected count,
> without modifying the engine's `Rc`/`RefCell` ownership or the VDBE
> opcode-dispatch loop.

Spec 013 makes two of its seven requirements architectural rather than
ergonomic — Req 4 (`Send + Sync`) and Req 7 (incremental rows) — and a wrong
guess in either forces a rewrite of the facade built on top. They interact:
streaming across a thread boundary means the statement handle holds cursor
state on the worker while the caller holds a `Send` handle.

A static read of the tree predicted the hypothesis would **fail on its second
clause**. `Vm` is public, but `fn dispatch` (`src/vdbe/exec.rs:704`) and
`fn run` are not, and `ResultRow` calls `Vm::emit_row`, which pushes into a
`Vec` *inside* the `Vm`. So streaming had to be impossible as a pure external
layer. The spike's job was to find the minimal engine change, prove it
additive, and price it.

## Setup

Apple Silicon (arm64, Darwin 25.6.0), `rustc` 1.98.0, `--release`, criterion
0.8. Oracle `sqlite3` 3.51.0 builds the fixtures.

Fixtures are generated by stock `sqlite3` and use `INTEGER PRIMARY KEY` (a
rowid alias) plus a *named* index — deliberately **not** a composite
`PRIMARY KEY`, because that shape triggers the `sqlite_autoindex_*`
corruption of spec 010/Req-8 and this spike must not measure a known bug.

`make test` gates `make bench`: the prototypes must agree on every row before
any timing is trusted (spike 013's precedent).

## Design

Four prototypes of one operation — run a `SELECT`, read its rows — differing
only in where the engine lives and how rows reach the caller.

| Prototype | Engine lives | Rows cross as | Engine change |
|---|---|---|---|
| `batch` | caller's thread | one `Vec<Vec<Value>>` | none |
| `worker_batch` | owned thread | one `Vec<Row>` per statement | none |
| `worker_stream` | owned thread | one row per message | **required** |
| `worker_chunked/N` | owned thread | `N` rows per message | **required** |

`worker_chunked` was not in the original design. It was added after
`worker_stream` measured 40x slower than the control on a full drain — see
Finding 4.

### The engine change

One public struct in `src/vdbe/exec.rs`, `+128/−49`:

```rust
pub struct Execution<'p> { /* vm, program, pc, steps, done, pending */ }

impl<'p> Execution<'p> {
    pub fn new(vm: Vm, program: &'p Program) -> Self;
    pub fn next_row(&mut self) -> Result<Option<Vec<Value>>, ExecError>;
    pub fn autocommit(&self) -> bool;
}
```

`run()` is then rewritten as a wrapper that collects `next_row` into the same
`Vec` it always returned. That is what makes the change additive rather than
parallel: the batch path and the streaming path are literally the same loop,
so a behaviour difference between them would be a bug in one rather than a
divergence callers must reason about.

**Additivity, measured:** `cargo test --locked` before and after — **1562
passed, 0 failed**, and every one of the 44 test binaries reports an identical
count. Only wall-clock numbers differ. `cargo clippy`, `cargo fmt --check`
and `check-mod-files` are clean.

## Finding

### 1. `Value` is `!Send`, and the spec does not say so

`Value::Text(Rc<str>)` and `Value::Blob(Rc<[u8]>)`
(`src/record/value.rs:15-17`) make `Value` itself `!Send`. Spec 013/Req-4 and
ADR-0034 both locate the `Send` problem in the pager (`Rc<dyn PageSource>`,
`Rc<RefCell<Pager>>`) and conclude that a worker which "creates its `Rc` graph
on a thread it owns and never lets it leave" is sufficient.

It is not sufficient, because **a result row is a `Vec<Value>`** and rows are
exactly the thing that has to leave. The boundary needs an owned
representation (`SendValue` here) and pays one allocation-and-copy per text
and blob value. Integers, reals and nulls cross free, so the cost is
proportional to text/blob payload rather than to row count.

This is a correction to the spec, not a blocker: the worker-thread strategy
survives, but Req 4's cost is one copy per non-scalar value, which neither
document currently accounts for.

### 2. The streaming primitive cannot assume one row per step

`Vm::emit_row` has three runtime callers, and
`src/vdbe/pragma.rs::integrity_check` emits *N* rows from a single dispatch —
one per problem found. A drain that assumed one row per step, and popped off
the back, would silently reverse `PRAGMA integrity_check` output. `Execution`
therefore moves rows through a FIFO. Found by reading `emit_row`'s callers
before writing the drain, not by a failing test.

### 3. Streaming bounds memory — at ~8 MB, not at ~0

Batch grows without bound: **137.7 MB** to deliver a 1,000,000-row result.
Streaming plateaus at **8.68 MB** and scales **1.03x** for 2.5x the rows.

Establishing that took three attempts, and the two failures are the
interesting part:

- **Attempt 1** varied database size and result size together, so the pager's
  page cache grew for a reason that had nothing to do with the API.
- **Attempt 2** held the database fixed and varied `LIMIT` — and streaming's
  peak *still* scaled 4.92x for 5x rows. That looked like the hypothesis
  failing. The cause was that `DEFAULT_PAGE_CACHE_CAPACITY` is 2000 pages and
  the 50,000-row fixture is only 369 pages: the whole database fit in the
  cache, nothing ever evicted, and peak tracked pages *touched*.
- **Attempt 3** needed a table whose *leaf* pages alone exceed 2000. A
  300,000-row fixture is 2,326 pages but ~700 of those belong to the unused
  `t_bucket` index, which a full table scan never touches — still under the
  bound. 1,000,000 rows finally forced eviction, and the plateau appeared.

So the correct claim is **bounded by the page cache**, i.e.
`min(pages_touched, capacity) x page_size`, independent of result size. Req 7's
scenario wording ("a large result is read without materializing it") should say
that; as written it invites an acceptance test that asserts near-zero growth
and fails for a reason unrelated to the API.

### 4. One row per channel message is unusable, and chunking fixes it entirely

`worker_stream` costs **~4.5 µs per row** in thread handoff — 40x slower than
the control on a full drain. That is the finding that would have been
discovered late and expensively, because it only shows up at scale: the
correctness tests pass at 2,000 rows without a hint of it.

Chunking removes it completely. At chunk 1024 the full drain is **7.30 ms**
against `worker_batch`'s **7.43 ms** — i.e. **chunking overhead reaches zero**,
and the residual 1.30x versus `batch` is the thread boundary plus the Finding-1
copies, not the streaming. Chunk 4096 buys nothing further (7.09 ms, inside
1024's confidence interval).

The trade is first-row latency, and it is mild: chunk 1024 still delivers row 0
in **328 µs** against batch's **5.36 ms** — 16x better, while giving batch
throughput and bounded memory. The knee sits between 256 and 1024.

### 5. Req 4 and Req 7 are both implementable; Req 1 was not reached

`Send + Sync` is proven at compile time (`const _: () =
assert_send_sync::<Connection>();`) rather than asserted in prose, and the
`Arc`-shared-across-four-threads, drop-releases-worker and
abandoned-stream-reuse scenarios all pass. The rows-affected count (Req 1) was
left out of scope when the spike was scoped to Reqs 4 and 7; nothing found here
contradicts the spec on it, and the static finding stands — there is no such
counter anywhere in `src/`.

## Conclusion

**The hypothesis is half right, and the half that fails is the useful part.**

- Req 4 (`Send + Sync`) needs **no** engine change — but it does need a
  boundary value type the spec does not mention, because `Value` is `!Send`.
- Req 7 (incremental rows) **does** need an engine change. It is small
  (+128/−49, one public struct), additive (1562/1562 tests unchanged), and it
  makes the existing batch path a wrapper over the new streaming one rather
  than a second code path.
- The facade **must chunk internally**. A literal reading of
  `Statement::next_row` as one-row-per-message is 40x slower than today's API
  on a full scan. Chunking at ~1024 rows erases that penalty entirely while
  keeping bounded memory and 16x-better first-row latency. The chunk size
  should be an implementation detail, not API surface — `ChunkedRowStream`
  here yields plain rows and hides it.

**Go**, with three corrections to spec 013 before it merges: name the
`!Send` `Value` problem in Req 4, restate Req 7's memory claim as
page-cache-bounded, and require internal chunking in Req 7.

### Ordering consequence

Req 7 should land **before** Reqs 2/3 (the `Connection`/`Statement` facade).
`Statement::next_row` has to sit on the streaming primitive; building the
facade on today's materializing `execute_with_db` and retrofitting streaming
afterwards means rewriting it.

### ADR

**An ADR is proposed** — but not by this spike, and not yet.
`Execution`'s shape (a streaming primitive with the batch path rewritten as its
wrapper) closes off the alternative of a second parallel execution path, which
is exactly the kind of decision the ADR convention covers. It belongs to the
shippable Req-7 ticket, not here, because this branch ships nothing. ADR-0034
itself needs superseding or amending on the `!Send` `Value` point regardless.

## Disposition

Throwaway. The `src/` patch on this branch is **evidence, not a deliverable** —
the real change lands via the Req-7 ticket with its own tests, ADR and review.
The crate stays as the reference implementation of the worker/chunking shape,
as spike 010's did.

Not reached, and deliberately out of scope: rows-affected (Req 1), the
`Connection`/`Statement`/`Transaction` ergonomics (Reqs 2/3), the durability
contract (Req 5), named-parameter refusal, and any write path. The
`sqlite_autoindex_*` corruption (spec 010/Req-8) is independent of all of it
and remains the higher-priority item.

# Part 2: can Jacob's three design decisions be settled by measurement?

Part 1 found three problems with spec 013 but left the *fixes* as open
design decisions, because each had a defensible alternative a spike had no
business choosing unilaterally. This part builds each alternative and
prices it, so the decisions are made on numbers instead of taste.

Same machine and method as Part 1. Two prototypes here (`worker_direct`,
`worker_adaptive`) only compile under the branch-local `Arc`-`Value` patch
described below.

## Decision 1 — where does the copy happen when a row leaves the worker?

`Value::Text(Rc<str>)`/`Blob(Rc<[u8]>)` make `Value` `!Send`, and a result
row is a `Vec<Value>`, so something has to give. Three options were
measured, not argued.

**Option (b), switching `Value`'s payloads to `Arc`, turned out to be
almost free — and nobody had ever measured it.** ADR-0013 and ADR-0017
rejected `Arc`, but they were arguing about the *pager*; `Value` was never
the subject.

The whole change is **+22/-17 across 6 files**, because nearly every
construction site writes `Value::Text(s.to_string().into())` and `.into()`
is identical for `Rc<str>` and `Arc<str>`. Only the ~12 sites that *name*
the type needed editing, plus 4 unused imports. `Rc<dyn PageSource>` and
`Rc<RefCell<Pager>>` are untouched, so both ADRs stay intact.

- `cargo test --locked`: **1562 passed / 0 failed** — identical to `Rc`.
- `Value` becomes `Send + Sync`, asserted at compile time.

Cost on the read path (`full_drain/batch` is single-threaded with no
boundary, so it isolates the tax):

| | `full_drain/batch` |
|---|---:|
| `Rc` payloads | 5.42-5.62 ms across runs |
| `Arc` payloads | 5.24-5.33 ms across runs |

**No measurable tax.** Individual comparisons showed `Arc` up to 5.6%
*faster*, which is not credible as a real gain — `Rc`-only runs already
spanned 5.42-5.62 ms, so the honest reading is that the difference sits
inside run-to-run variance.

And the boundary saving is large, because the copy disappears entirely:

| Full drain, 50,000 rows | Time |
|---|---:|
| `batch` (control, no boundary) | 5.31 ms |
| `worker_chunked/1024` (owned copy, option a) | 7.34 ms |
| `worker_direct/1024` (no copy, option b) | **5.13 ms** |

`worker_direct` matching — slightly beating — single-threaded `batch` is
real rather than noise: with `sync_channel(1)` the worker builds the next
chunk while the caller drains the previous one, so the thread boundary
buys pipelining once it stops costing copies.

**Finding: option (b).** A `Send` API for a 39-line diff, no measurable
engine cost, and it removes ~30% of the boundary cost that option (a)
pays forever. Option (a) remains the fallback if the `Arc` change is
judged too invasive on principle, but the measured case against it has
evaporated.

## Decision 2 — weaken the memory promise, or make it true?

Part 1 found streaming's peak floored at ~8 MB, contradicting Req 7's
scenario. The assumed alternatives were "restate the claim" (free) or
"build scan-aware page eviction" (a large separate ticket).

**Both were wrong: the floor is a single constant.** Sweeping
`DEFAULT_PAGE_CACHE_CAPACITY` (`src/pager.rs:63`) against a 1,000,000-row
result:

| Capacity | Ceiling | `batch` peak | streaming peak | Ratio |
|---:|---:|---:|---:|---:|
| 2000 pages | 8.19 MB | 137.7 MB | 8.68 MB | 15.9x |
| 256 pages | 1.05 MB | 130.2 MB | 1.10 MB | 118.8x |
| 64 pages | 262 KB | 129.4 MB | **291 KB** | **445x** |

Streaming peak tracks the ceiling almost exactly and stays flat in result
size (1.00x for 2.5x rows read) at every setting. The existing LRU already
does the job; the constant is simply tuned for a general workload.

Time cost of dropping to 64 pages (`full_drain`, 50,000 rows):

| | 2000 pages | 64 pages | Change |
|---|---:|---:|---|
| `batch` | 5.326 ms | 5.316 ms | none (p = 0.42) |
| `worker_direct/1024` | 5.042 ms | 5.266 ms | **+4.5%** (p < 0.05) |

**Finding: 4.5% time for 28x less memory**, and no new machinery. A
sequential scan reads each page once, so a small cache costs almost
nothing on this access pattern — the penalty would land on random/indexed
access, which is worth checking before making it a global default.

So Req 7 does not need its promise weakened *or* a new eviction subsystem.
It needs a streaming connection to be allowed a smaller cache. The right
spec wording is a bound the caller can choose, not a fixed ~8 MB.

## Decision 3 — is the chunk size public API or a hidden constant?

Part 1 measured fixed chunk sizes and found a real trade: big chunks give
throughput, small chunks give first-row latency. That trade is what would
have justified exposing a knob. Option (c), a growing chunk (1, 2, 4, ...
up to a cap), was untested.

| Strategy | Full drain (50k) | Time to first row |
|---|---:|---:|
| `batch` (control) | 5.26 ms | 5.69 ms |
| 1 row per message | 231.6 ms | 45.5 µs |
| fixed chunk 1024 | 5.27 ms | 357 µs |
| **adaptive, cap 1024** | **5.52 ms** | **50.2 µs** |

**Finding: the trade does not exist.** Adaptive lands within 5% of the
best throughput and within 10% of the best latency, simultaneously. It
needs no knob, so the chunk size stays an implementation detail and never
enters the public API.

This also dissolves the question Part 1 raised about which SQE use case to
optimise for — the catalog pointer store and the arbitrary-attached-database
case are both served by the same strategy.

## Conclusion to Part 2

All three decisions are answerable from measurement, and in each case the
answer is the *better* option rather than a compromise:

1. **Switch `Value` to `Arc`.** 39 lines, no measurable cost, removes the
   boundary copy permanently. The ADRs that seemed to forbid this were
   about the pager.
2. **Let a streaming connection choose a smaller page cache.** 4.5% time
   for 28x memory. Req 7's promise can be nearly kept rather than
   weakened or deferred.
3. **Adaptive chunking, no knob.** Both properties at once; the trade
   that would have justified a configurable API is not real.

Two caveats worth carrying into the tickets. The `Arc` measurements are
same-machine and same-session, and a -5.6% "speedup" from adding atomics
is a reminder that the noise floor here is a few percent — the claim is
"no measurable tax", not "faster". And the small-cache result is measured
only on sequential scans; the random-access cost is unmeasured and is the
obvious next thing to check before changing any default.

### ADR consequences

Part 1's ADR verdict stands, and Part 2 adds one: Decision 1 needs an ADR
of its own, because switching `Value` to `Arc` narrows what ADR-0013 and
ADR-0017 were taken to mean. Neither actually ruled on `Value`, so this is
a clarification with new evidence rather than a superseding decision — but
it should be written down, since the natural reading of those two ADRs is
that `Arc` anywhere was settled against.
